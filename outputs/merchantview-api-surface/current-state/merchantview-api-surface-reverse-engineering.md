# Reverse Engineering: MerchantView API Surface

**Scope:** Source = Merchant View. Target = Atlas. Mode = Quick, amended to Strict for the MV side.
NAB-specific API usage data was requested from Looker, Coralogix, and Mixpanel.

**Amendment (2026-09-23):** MV-side findings are now grounded primarily in the official MerchantView API documentation (`org-brain/MV-API-docs-3.pdf`, November 2023), EverC's published partner-facing API reference — a more authoritative source than the original code-only pass, since it documents the contracted external behavior rather than an inferred internal implementation. Corrections and additions from this document are marked inline. Code citations from the original pass are kept where the doc doesn't cover implementation detail (e.g. internal gateway modules, entitlement flags).

## Executive Summary

- MV exposes a documented partner API surface: merchant management (full CRUD including delete/soft-delete), URLs, contact information (addresses/aliases/emails/phones, full CRUD), scans, findings (including snooze and dispute status), risk matrix configuration, callbacks, login/logout, plus a newer async scan-intake service found in code but not in the published doc.
- **Auth correction:** the published API uses bearer token authentication (`POST /api/v4/login` returns `access_token`; every other call requires `Authorization: Bearer <TOKEN>`) — not purely internal session/role-based auth as the original pass concluded. This is a session token obtained via a login call, not an OAuth client-credentials/API-key mechanism; no client-credential issuance endpoint is documented, which stands as a real gap for machine-to-machine partner integration without an interactive login step.
- **Callback mechanism, corrected and expanded:** the doc describes two supported delivery mechanisms — REST (a customer-hosted HTTPS endpoint EverC pushes to) and AWS SQS (queue-based, with S3 fallback for payloads over 256KB) — both configured out-of-band via EverC Support, not through a self-service admin API endpoint. The original pass's citation of an admin-gated `/api/v4/callback` CRUD endpoint is not found in the published doc; callback *configuration* itself is a support-ticket process, not an API. `callbackType` currently has one documented value, `MERCHANT_SCAN_AVAILABLE`.
- API access is entitled per client today via `Bank` domain flags (e.g. `CAN_SCAN_WEB_ID`, `MONITORING_PACKAGE`, `AUTOMATED_SCAN`) — code-sourced, not in the published doc. A `UNIFIED_PLATFORM_ACCESS` flag already exists on that model but it is unconfirmed whether it drives any live routing.
- The doc is versioned `/api/v4` throughout with no mention of an older unversioned generation; the original pass's "two live generations" claim is code-sourced only and not corroborated by the partner-facing doc, though that doesn't rule out an internal legacy path the published doc simply doesn't document for partners.
- **NAB-specific usage data could not be pulled.** Looker has no available MCP tool in this environment, Coralogix is not authorized for this session, and Mixpanel (both MerchantView Production and Atlas Production projects) has no API-related events and no client/bank-identifying property at all — it only instruments portal/UI usage, not API traffic.

## Current Behavior by Platform

**Merchant View** — per the official API doc (`MV-API-docs-3.pdf`, Nov 2023) unless marked code-sourced:

- **Merchant management**, `/api/v4/merchants`: create (POST, up to 100 merchants per call, idempotent on `uniqueId`), retrieve single/multiple (GET), search with filtering/sorting/pagination (GET with query params: `legalName`, `uniqueId`, `url`, `merchantRisk`, `findingType`, `findingCategory`, `active`, `monitoring`, `lastScanned`, `onlyLatestScan`, `isMerchantUrl`), update (PUT), deboard/delete single or multiple (DELETE — a soft-delete: `active=false`, `merchantStatus=deleted`, merchant record and history retained), start/stop monitoring (`PUT /merchants/<ID>/monitoring`).
- **Merchant URLs**, `/api/v4/merchants/<ID>/urls`: create (POST, triggers a new Quick Insights scan), retrieve single/multiple (GET), update MID/DBA/type only — the URL string itself is immutable (PUT), soft-delete single or multiple (DELETE; deleting all URLs removes the merchant from the portfolio).
- **Merchant contact information**, `/api/v4/merchants/<ID>/{addresses|aliases|emails|phones}`: full CRUD (GET/POST/PUT/DELETE) on each contact type, single or multiple by ID.
- **Scans**, `/api/v4/merchants/<ID>/scans`: retrieve all, latest, or specific scan(s) by ID, for one or multiple merchants; network/ecosystem evidence at `/scans/<ScanID>/network`. Scan types: `quick_insights` (onboarding) and `monitoring` (periodic, SLA-based, no API call required once a merchant is onboarded and monitored). **Scan submission is implicit** — a scan is triggered by merchant creation (`requestScanType` field), by adding a new URL, or automatically on the monitoring cadence; the doc does not document a standalone "submit a scan for an existing merchant" POST endpoint distinct from these triggers.
- **Findings**, `/api/v4/findings/<ID>`: retrieve (GET), edit `reviewerNotes` and `findingStatus` (PUT) — status values `not_checked`, `in_progress`, `allowed`, `remediated`, `review_completed`, `rejected`, plus read-only system-set values `disputed`, `false_positive`, `dispute_rejected`, `no_action_required`; a `disputed` finding is not editable until the dispute resolves. Finding evidence retrieval at `/findings/<ID>/evidence` — seven evidence types documented (text, screenshot, keyword, MCC, MCC mismatch, link, network) plus six "insight" sub-types (IP country, page views, registrant country, reputation, site data, WhoIS).
- **Snooze**: documented as a Snooze Object (`findingStatus` to apply when the snooze period ends, `period` in days, read-only `snoozedDate`/`plannedDate`) — confirms snooze exists as a finding-status feature; the doc does not show its own endpoint path, only the object shape.
- **Risk Matrix**, `/api/v4/riskMatrix`: retrieve (POST, by category name(s) or all) and edit (`POST /riskMatrix/edit`) the risk severity (`no_risk`/`low`/`medium`/`high`/`critical`) assigned per finding category, separately for reported vs. unreported (ecosystem) domains. Not present in the original code-only pass.
- **Login/Logout**: `POST /api/v4/login` (only call not requiring the Authorization header) returns a bearer `access_token` and `roles`; `POST /api/v4/logout` revokes it.
- **Callbacks**: sent for completed Quick Insights and Monitoring scans, one callback per scanned merchant covering all its URLs' scan results. Two delivery mechanisms, both configured via EverC Support (not a self-service API): REST push to a customer-hosted endpoint, or AWS SQS (with S3 for message payloads over 256KB, requiring cross-account role/bucket/queue/region setup). `callbackType` enum currently has one value, `MERCHANT_SCAN_AVAILABLE`.
- **Ecosystem/Network evidence**: a merchant's "ecosystem" is the sum of reported and unreported (discovered) online activity, connected via typed edges (20 documented edge types, e.g. `Website Has IP`, `Whois Has Registrant Phone`, `Website Has PSP`) between typed nodes (8 node types: PSP key, domain, email, IP address, phone, address, geo-address, alias). Retrieved via `/scans/<ScanID>/network`.
- **MCC classification and mismatch**: MCC evidence type distinguishes `detected` (found by MerchantView), `reported` (declared by merchant), and `reported_and_detected`; a separate MCC Mismatch evidence object compares a reported MCC's group against a detected MCC's group when they diverge.
- **Objects and error handling**: fully typed object reference (Merchant, URL, Address, Alias, Email, Phone, Scan, Finding, Snooze, Callback, Scan Item, Evidence — by type, Network, Search Results, Account) and a structured error format (`message`, `status`, `extendedMessage` array of `{errorValue, field, message}`), with documented 4xx/5xx codes including `409 Conflict` for duplicate-merchant and invalid monitoring-restart attempts.
- **Not covered by the published doc, code-sourced only (original pass):** a WebID-specific `/api/v4/webid/merchants/...` endpoint set — the doc mentions WebID only as a URL-detection *mechanism* inside Quick Insights ("It also can use the WebID mechanism to retrieve a URL for the merchant, if one was not provided"), not as a separate scan/report/sync-report product with its own endpoints; a separate async `/api/v1/scan-request` Kafka/SQS gateway (`gateway/merv-gateway-splitter`); bulk operations beyond the documented multi-ID GET/DELETE patterns (bulk save/update for findings, screenshots, scan items, merchant ownership); an admin-facing `/api/v4/callback` CRUD endpoint (the doc shows callback *configuration* as an out-of-band support process, not an API); reporting/export endpoints (report list/generate, audit export, admin login report); transaction/billing endpoints (`TransactionApi`, `TransactionBulkApi`, `AdminBillingApi`); account/bank endpoints beyond the Account Object's `id`/`name` fields shown in the doc; user management/password reset endpoints; internal bank-server↔global-server gateway module (scan monitoring, screenshot generation).

## Business Rules to Preserve

1. Merchant identity is enforced by `uniqueId` as a one-to-one key with `legalName` — sending an existing `uniqueId` merges new fields into the existing merchant rather than creating a duplicate; changing `uniqueId` to one that already exists, or merging two merchants under one `uniqueId`, is rejected.
2. Merchant creation is capped at 100 per API call; exceeding it returns a specific error message rather than a generic 400.
3. A URL's `url` field is immutable once created — changing the URL string requires delete-and-recreate, not update. MID, DBA, and URL type remain editable.
4. Deboarding (deleting) a merchant is a soft-delete: the record persists with `active=false`, `merchantStatus=deleted`; findings and risk history remain retrievable; a deboarded merchant can re-enter the portfolio only via a new Quick Insights scan.
5. Deleting all of a merchant's URLs implicitly removes the merchant from the portfolio (not merely its last URL).
6. Restarting monitoring (`PUT /monitoring`) is allowed only for merchants whose monitoring was previously stopped — not for never-onboarded, already-monitored, deboarded merchants, or merchants with no URLs; violating this returns `409 Conflict`.
7. A finding's `disputed` status is not editable via the standard edit-status call until the dispute resolves — dispute resolution is a separate, gated workflow (`Dispute Status` enum: submitted, in progress, additional info required, rejected, accepted, withdrawn).
8. Risk severity is configurable per finding category, and separately for reported vs. unreported domains — this is an account-level customization (Risk Matrix), not a fixed system default, meaning risk scoring behavior can legitimately vary per client.
9. Callback delivery is opt-in and configured out-of-band via EverC Support (REST endpoint + auth method, or AWS SQS cross-account details) — there is no documented self-service API to create/edit/delete a callback subscription.
10. AWS SQS callback payloads over 256KB are not delivered inline; the message instead references a payload stored in an S3 bucket the client provisions and grants EverC cross-account access to.
11. Finding status and reviewer notes persist with a site across monitoring scan updates only "as long as they remain relevant" (the doc's example: a note on an `Online` finding disappears once the site goes offline) — history remains accessible via past scans, but the *current* finding view can silently lose carried-forward notes when the underlying condition no longer applies.
12. API access is entitled per bank/client, not uniform — gated by `BankFlagEnum` values on the `Bank` domain object (`CAN_SCAN_WEB_ID`, `CAN_SCAN_QUICK_INSIGHTS`, `MONITORING_PACKAGE`, `SNOOZE_FINDING_STATUS_ENABLED`, `AUTOMATED_SCAN`, `MANUAL_RELEASE_*`, `UNIFIED_PLATFORM_ACCESS`) — code-sourced (original pass), not shown in the published doc.
13. A disabled bank is blocked from all API actions except an explicit allow-list (login, admin, metrics, billing, user management) — `BankActivationCheckInterceptor` — code-sourced (original pass).
14. Findings snooze is a separately entitled action (`SNOOZE_FINDING_STATUS_ENABLED`) per the original code pass; the published doc confirms the Snooze Object's shape but not this entitlement gating.

## Gaps

- No client-credential/token issuance mechanism (API key, OAuth, client secret) is documented for external partner API callers — only bearer-token-via-login was found in the published doc, and only session/role-based auth was confirmed in code. If NAB or any partner calls these APIs machine-to-machine today, the credential model requires an interactive-equivalent login step, which is a real integration gap if fully unattended access is required.
- Risk-scoring business logic behind these endpoints (`merv-global-services`) was not explored — flag if migration scoping needs it.
- The published doc does not document a standalone scan-submission endpoint separate from merchant-create/URL-add/monitoring-cadence triggers — if MV in practice supports an explicit "rescan this merchant now" API call beyond those triggers, it is undocumented in this reference and unconfirmed.
- Callback configuration itself has no self-service API — every new callback destination requires a support ticket to EverC. This is a genuine MV limitation worth surfacing regardless of the UP migration question.

## Conflicts / Product Decisions

- Whether `UNIFIED_PLATFORM_ACCESS` currently routes any live traffic to UP or is a dormant/planned flag is an open question with a real migration-sequencing consequence — recommend confirming with engineering before assuming UP cutover readiness for any client.
- **PRD drift flag:** the original reverse-engineering pass described an admin-gated `/api/v4/callback` CRUD API as part of MV's documented surface, and the companion gap document (`mv-to-up-api-gaps.md`) built a "confirmed gap" conclusion for Atlas partly on that basis. The official API doc does not support that endpoint existing as a self-service partner API — callback setup is a support-ticket process. This doesn't necessarily mean the original code citation was wrong (an internal admin tool distinct from the partner API is plausible), but it does mean the *product* framing of "MV has a callback config API UP lacks" needs to specify which surface (partner-facing vs. internal-admin) before this gap is called final. Recommend the PM confirm which framing matters for the migration decision.
